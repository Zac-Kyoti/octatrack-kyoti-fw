# SP12 mid/side: the design kept for reference

On 2026-10-15 the user moved VARISPEED_EMUS's SP12 engine back to full stereo. This file keeps
the mid/side design it replaced, so it can be restored. The code itself is preserved by the git
tag **`ref/sp12-midside-vem7`**: commit `4d1d54f` on branch `repitch-rewrite`, the VEM7 state,
whose image `140C_VEM7` (syx `3a35a085…`) runs this design.

## What it was

The user chose it in listening pack 3 (2026-10-06, rev 17). It was hardware-tested from rev 17
on, and the raw outputs 7/8 became the shipped form.

- **Mid** = (L + R) / 2 goes through the full SP-1200 path:
  - the 8-tap virtual ADC at the SP's 26.04 kHz clock;
  - 12 bits;
  - the band-limited 10-tap render to 44.1 kHz;
  - raw, as the SP's outputs 7/8 (no channel filter).
- **Side** = (L − R) / 2 is read **clean**, with the OT's own 2-tap linear read. It is read as
  far behind the OT's position as the mid path delays the mid: c + 1 frames, plus
  `MS_SIDE_DELAY` (5.83 for raw) increments, plus a smoothed copy of the SP's truncating read
  shift (a one-pole, 2^−`MS_LAG_SHIFT` = 2^−4 per tick).
- **L, R** = mid ± side. Anti-phase content lives only in the side, so nothing cancels.
- **The side average** `(s + s[n−1]) / 2` existed only in the channel-6 build (`side_avg`); the
  raw build has none.
- **Why:** it kept stereo width and panned treble clean (only the mid aliases), and it cost less
  than two full SP paths at the time.

## Cost and memory (VEM4 to VEM7, the optimized kernel)

- **SP12 per voice:**
  - DSP instructions per output sample: 92 median, 110 worst;
  - datasheet cycles: 114 median, 136 worst;
  - hardware-calibrated (`varispeed_emus_dsp_profile.py` ~hw, worst over 0.5–1.99×): **217.2**, which
    is the load guard's `VG_SP12 = 218`.
- **Kernel:** 429 of 432 P words in SPRING's first run. X: 465 table words. Y:$A00–$FFF
  (layout 6, slot tag `$5A5A09`); the RPSP slot is `$20` words per track.

## Where it lives at the tag

- `tools/varispeed_emus_model.py`: the float design (`Engine(..., ms=True)`), `MS_OUT`,
  `MS_CHANNEL`, `MS_SIDE_DELAY`, `MS_LAG_SHIFT`, `side_avg`; and the bit-exact twin `DspExact`
  (mid + side).
- `tools/varispeed_emus_dsp_src.py`: the constants (`SIDEC`, `KD`, `LSSH`, `LSMUL`, `TAGSP`, ...) and
  the Y layout.
- `tools/varispeed_emus_dsp.asm`: the kernel, with `zqsp` … `zqout` for the mid/side render.
  `reference/handoffs/VARISPEED_EMUS_DSP_OPT.md` lists every optimization made to it.
- `octabam-modules/varispeed-emus/vem_dsp.asm` and `vem_dsp_ptable.py`: octabam's form,
  generated by `tools/varispeed_emus_dsp_octabam.py`.
- `tools/varispeed_emus_dsp_engine_check.py`, `varispeed_emus_dsp_octabam_check.py`,
  `varispeed_emus_dsp_boot_check.py`: its gates (80/80 + 8/8, 264/264, boot PASS).
- History: NOTES.md "Session 120 continued (10)" (the rev 17 design) and the 2026-10-08 entries
  (channel 6, raw 7/8, channels 1/2). The channel-6 and channel-1/2 variants were dropped from
  the kernel in `1be8556` and live in the history before it.

## To restore it

Check out those files from the tag:

    git checkout ref/sp12-midside-vem7 -- tools/varispeed_emus_model.py tools/varispeed_emus_dsp_src.py tools/varispeed_emus_dsp.asm

Then:
1. regenerate octabam's form (`python3 tools/varispeed_emus_dsp_octabam.py`);
2. set the guard's `VG_SP12` back to 218;
3. rebuild, and run the three gates.

The ColdFire side is the same for both designs: the engine tag and the guard do not depend on
mid/side.

**The tag is local until it is pushed:** `git push origin ref/sp12-midside-vem7`.
