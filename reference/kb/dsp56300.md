# The DSP side — chip, boot, program layout

`COVERAGE.md` scopes DSP patching **out** of this repo (ColdFire-only). But the
ColdFire *uploads* the DSP program, so the boot path and load map are shared
ground — and **octabam** has mapped the DSP thoroughly. Keep this current so a
future "does this need DSP?" question has an answer without re-deriving it.

Primary source: **octabam** (`refs/octabam/docs/`), which is itself a
ColdFire+DSP sibling of the octamax lineage — its ColdFire function names line
up with ours.

---

## Chip

> source: `refs/octabam/docs/CHIP.md` @ `e1dcfa9` · fetched 2026-09-02 · confidence: **C** (octabam marks it "measured, read off the part")

- **One chip: DSP56721** (not a 56300-series exactly — 56720/56721 family, dual-core).
- **Two cores.** Core 0 = tracks 5–8, Core 1 = tracks 1–4. ~4535 cycles/sample each.
- Each core: own P memory; **shared 64K** at `Y:0x30000–0x3FFFF`.
- Per-track chain: `FX1 → FX2 → gain → bookkeeping`. FX1/FX2 are **slots**, not chips.
  FX1 = 3072 words Y, FX2 = 16384 words Y (why reverbs are FX2-only).
- Program space ~2724 words/core payload.

⚠️ **Contradiction with our `ARCHITECTURE.md`**, which "assumes a single DSP56xxx".
octabam's boot map (below) shows the upload sequence running **twice** with a GPIO
toggle, two bootstraps + two payloads, near-identical X/Y layouts at different
bases. Treat "two cores/banks" as the better-supported model.

## Boot / upload path (ColdFire side — overlaps `memory-map.md`)

> source: `refs/octabam/docs/DSP.md` @ `e1dcfa9` · fetched 2026-09-02 · confidence: **C**

`FUN_40001e50`, called from boot at `0x4000050c`:

| Step | Detail |
|---|---|
| `move.w #0x81,(0x20000000)` | DSP control = start (matches our `FUN_40001d4c` note: "stream starts `0x20000000 = 0x81`") |
| `FUN_40001d4c(0x400e21e0, 0x96, 0x31000)` | bootstrap A → `P:0x31000` (50 words) |
| `FUN_40001b18(0x400e2324)` | payload A, 79 563 B (serves tracks 5–8) |
| GPIO `0xfc0a400c` flipped, `#0x81` again | second pass |
| `FUN_40001d4c(0x400e2276, 0xae, 0x32000)` | bootstrap B → `P:0x32000` (58 words) |
| `FUN_40001b18(0x400f59ef)` | payload B, 77 061 B (serves tracks 1–4) |
| `move.l #0xfff0000,(0xfc00801c)` | FlexBus / chip-select config |

ColdFire→DSP payload source addresses: **`0x400e21e0`, `0x400e2276`, `0x400e2324`,
`0x400f59ef`**. (Our NOTES already touch `0x400e21e0` / `0x400d7400` region.)
`file_offset = vaddr − 0x40000400`.

DSP dispatch: both FX slots share one table — six `jsr (r2)` at `P:0x0041e`,
indexing `X:0x215` / `X:0x235`. FX1 id from `r6+$1b`, FX2 id from `r6+$1c`.

## If a feature ever needs the DSP

octabam's whole toolchain (`refs/octabam/`) is the reference: `dsp/` assembler,
`modules/*/manifest.py` registry, `make bus REMIX=…` build, collision checker.
It targets **MKII**; MKI DSP is very likely the same silicon but the OS image
offsets differ — verify against our own `section_3_MAIN_OS.bin` before reusing
any address literally.

## Module load-map parser — octa-bt-pt (runnable against our image)

> source: `refs/octa-bt-pt/tools/dsp_modmap.py` @ `e970dd0` · fetched 2026-09-02 · confidence: **L** (author flags field-order ambiguity, tries both)

`FUN_40001b18(ptr)` walks the payload as **24-bit little-endian words**: optional
3-header then optional 4-header (6 B each), then records — leading word = memory
space (`0`=P `1`=X `2`=Y), fields `(count, addr)` or `(addr, count)` (ambiguous —
parser tries both), terminated by a word `> 3`.

| Payload | ColdFire src | length | DSP target | serves |
|---|---|---|---|---|
| bootstrap A | `0x400e21e0` | `0x96` (50 w) | `P:0x31000` | — |
| bootstrap B | `0x400e2276` | `0xae` (58 w) | `P:0x32000` | — |
| payload A | `0x400e2324` | `0x136cb` (79 563 B) | self-describing | tracks 1–4 (octa-bt-pt) / 5–8 (octabam) |
| payload B | `0x400f59ef` | `0x12d05` (77 061 B) | self-describing | the other four |

⚠️ octabam and octa-bt-pt **disagree on which payload serves which tracks**
(A=5–8 vs A=1–4). Settle empirically before relying on it.

`python3` port of `dsp_modmap.py` against `out/raw/section_3_MAIN_OS.bin` is the
concrete next step for our own DSP work (it also has `--extract` / `--dumpmem`).

## Known DSP bug — AMF `mpysu` → `mpyuu`

> source: `refs/octa-bt-pt/tools/generate_streamlit_patch.py` @ `e970dd0` · fetched 2026-09-02

Long-standing Octatrack AMF (filter env-follower / frequency) bug. Fix = one
opcode per payload in **P space**: `mpysu` (`0x01278d`) → `mpyuu` (`0x0127cd`) at
`P:0x01bef` (payload A) and `P:0x019af` (payload B). Signed×unsigned multiply
where both operands are unsigned. Candidate to fold in if we ever ship a DSP patch.

## octabam's RTOS fork + `dsp_host` (2026-09)

> source: `refs/octabam/docs/{RTOS_FORK,CHIP,XBUS,FAILURE_MODES}.md` @ `2f241e1`

octabam's 200+ Sep-2026 commits are its own **MKII DSP-effect-addition** work
(a "bus screen", reverb/delay engines, cross-core accumulator fixes) — the DSP
side our `COVERAGE.md` scopes out. Two things transfer regardless:

- **`dsp_host` alone is single-core and pokes `r6` directly.** Any bug that needs
  the second DSP core or the shared-window accumulators — cross-core bus glitches,
  cycle overruns — **never reproduces off the unit**; and a page-2 param looks
  live locally even when the real unit publishes nothing (see the publish path in
  `memory-map.md`). Believe the hardware. (`XBUS.md`, `PARAM_PAGES.md`.)
- After an OS upgrade the DSP state RAM is **not** cleared; an engine with a valid
  warm-up tag runs on stale buffers → garbled audio until a reboot. **Power-cycle
  after every flash before judging anything.** (`FAILURE_MODES.md`; our
  `FLASHING.md` says the same.)

**Update `04b8512` (Sep 2026): the ColdFire PORT (`tools/ot_emu`) now folds
`dsp_host` in** — a headless C++ machine that boots the RTOS *and* runs both
DSP56321 cores, renders ESAI audio, and is bit-identical to `dsp_host` on the
one-aux bus (O12). It reproduced a real hardware audio bug and found its cause
(O11: the stock DSP dispatcher bumps `r7` **three times per track**, the third
unconditional after FX2 — any module keyed on `r7`/`r6`/instance blocks must be
measured under the port, never modelled in `dsp_host`). Effect coefficient
blocks: FILTER `X:0x2c0` = FX2 instance, `X:0x3a0` = FX1 (`r6` base `X:0x2c3 /
0x3a3`). Full write-up: `techniques.md` "the ColdFire PORT".

The ColdFire-side kernel/scheduler decode from the same fork is in
[`memory-map.md`](memory-map.md) "Kernel / RTOS"; the parameter→engine publish
path (page 1 posts to the DSP queue, page 2 rides the per-frame copier only) is
in "Parameter value → the engine".

## The DSP56300 core itself — `dsp56300/dsp56300`, now tracked directly (2026-09-16)

> source: `refs/dsp56300/README.md` + git log @ `46aa691` (branch `dsp56300`,
> **not** `main` — `main`'s tip is stale, 2026-05-25) · fetched 2026-09-16 · **C**

Everything above (`dsp_host`, `tools/ot_emu`, octabam's whole DSP-side
harness) ultimately renders through **this** project: a generic, cycle-level
Motorola/Freescale/NXP DSP56300-family emulator (interpreter + JIT, GPLv3,
outputs a static library only — no app of its own). It's the same chip family
the Octatrack's audio DSP is built on (used across Access Virus, Nord Lead
3/microwave II, and others of that era). octabam does **not** track this
repo's tip — `scripts/setup.sh` hard-pins a specific commit
(`DSP56300_PIN = c051afad…`, dated **2026-07-28**) into `vendor/dsp56300`,
deliberately, for build reproducibility (`refhash.sh`, "the author's own build
is the oracle" — see octabam's `CLAUDE.md`).

**Currency check (2026-09-16): octabam's vendored pin is 132 commits / ~7
weeks behind this repo's current tip.** Landed since the pin: real
instruction-semantics fixes and additions — `DOR aa`, `DO FOREVER`, `MACRI`,
`LRA Rn`, `TRAP`/`TRAPcc`/`ILLEGAL` in both the interpreter and JIT; `MOVEP`
between P memory and low I/O addresses; `MOVE(M)` with an absolute short
address; `CMPU` now sets `N` from the unsigned borrow; a CCR overflow-flag
pass across `ADD`/`SUB`/`CMP`/`INC`/`DEC`/`ABS`/`ADDL` plus `ROL`/`LSL`/`CLB`/
bit-test-jump/48-bit-transfer fixes; `ADC`/`SBC`; ESAI transmit-underrun
logging. None of this is confirmed to matter for octabam's shipping effects
(their own `refhash` gate would show it if a rebuild against tip changed
anything audible) — flagging it because a chunk of these are exactly the
class of bug (flag semantics, saturating-instruction edge cases) that has
already cost octabam multi-day sessions per its `CLAUDE.md` traps list, and a
DSP56300-semantics question we hit ourselves should be checked against this
repo's current `dsp56kEmu` source and its test suite before assuming
octabam's vendored copy is authoritative.

**Why we track this repo and not `dsp56300/gearmulator`**: gearmulator (the
same GitHub org's flagship project — VST/AU/CLAP/LV2 emulations of Virus,
microQ, Nord Lead, JP-8000, the Sound Canvas family) pulls this exact repo in
as its own `source/cpu/dsp56300` submodule; nothing in the rest of
gearmulator's tree (JUCE plugin UI, other CPUs for other synths' host
processors, installers) bears on an Octatrack-shaped ColdFire+DSP56300
machine. Reviewed 2026-09-16, not added as a separate manifest entry —
tracking `dsp56300/dsp56300` directly gets the useful part with none of the
unrelated bulk.
